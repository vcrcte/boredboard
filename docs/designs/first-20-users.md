# Design: First 20 users — the share link that's better than a Spotify link

Generated by /office-hours on 2026-10-13

## Problem Statement
The founder asked: "how do i get my first 20 users?" boredboard is live (social board for curious people; music, articles, books, reflections; per-friend shelves approved in DESIGN.md), but in production there is 1 visible profile, 11 posts (9 music, all by the founder, last one 2026-10-06) and 0 follows. The question is not distribution yet. It is whether anyone besides the founder will share there, and why they would.

## Demand Evidence
- None yet. The founder's answer to Q1: "No evidence yet, it's mostly me."
- The one real behavior is the founder sharing music through the iOS Shortcut (9 of 11 posts). It stopped on 2026-10-06.

## Status Quo
- Friends already share tracks and links in group chats (WhatsApp, Messenger, Discord). That is the habit to work with, not against.
- What the group chat does badly, from the session: links get buried, nobody can find last month's track, nobody sees each person's taste, and in mixed groups a Spotify link is useless to a Deezer or Apple Music listener. The last point is the second opinion's; it has not been confirmed with a real user yet.

## Target User & Narrowest Wedge
- **Target:** the music curator of each group chat, the 1-2 people who share the most tracks. The founder declined to name specific people ("we dont care about the names honnestly"). The plan therefore starts by finding them (see The Assignment).
- **Narrowest wedge:** one link per shared track. When it's pasted in the group, it opens the track in each receiver's own streaming app and shows the sharer's shelf. Music only.

## Constraints
- Solo founder; existing stack: Next.js on Vercel, Supabase, iOS Shortcut route (`app/api/shortcuts/music`), Chrome extension, `lib/music.ts`, `/api/og`.
- The Odesli/song.link public API is closed (`PUBLIC_API_ACCESS_DEPRECATED`, checked 2026-10-13). Cross-service matching must be built in-house: Deezer API and iTunes Search (free, no key), Spotify Web API (free, needs app credentials), and a YouTube search link.
- Receivers have no account and must not need one.
- Capture works only on iOS (Shortcut) and desktop Chrome (extension); Android curators can't take part in this test.

## Premises
1. There is no demand evidence yet. The first goal is not 20 signups but 3 people, besides the founder, sharing on boredboard on their own for 2 weeks. (agreed)
2. The habit lives in group chats. boredboard must not ask people to post somewhere else instead; it makes the group better: memory, plus each person's taste. (agreed)
3. The target is each group's music curator, who pulls the rest of the group in. (agreed)
4. **Revised after the second opinion:** the link pasted back into the group must be better for the receiver than the native link: it opens in their own app and shows the sharer's shelf. That advantage, not the preview alone, is what spreads boredboard. (agreed)
5. Music first: it's the behavior that exists, and the Shortcut and extension already support it. (agreed)

## Cross-Model Perspective

- **Steelman:** "a memory and identity layer for the music friends already swap in group chats". The chat keeps the conversation; boredboard keeps the memory and gives credit.
- **Most revealing answer:** "we dont care about the names honnestly". The plan depends on a specific curator nobody has named, so the real problem is a missing first user, not a distribution channel.

- **48-hour prototype:** a universal link (`/s/abc`) with an OG preview ("partagé par Victor · 9e morceau cette semaine"), a landing page that opens in the receiver's app plus the sharer's last 8 tracks and "Partage le tien", and click/app logging. Skip feed, follows and the new dashboard for the test. (Its Odesli dependency no longer works; see Constraints.)

## Approaches Considered
- **A) Concierge test, no code:** invite 5 curators and install the Shortcut with them. Ruled out as the whole plan, because the link they paste is no better than Spotify's, so nothing spreads. Its outreach is kept as the Assignment.
- **B) Universal share link + test:** chosen (below).
- **C) Group shelf (one boredboard page per WhatsApp group):** ruled out for now, because it adds groups, invites and permissions before anyone else uses the product.

## Recommended Approach
**B: a universal share link, then a 2-week test with 5 curators.** Wireframe: `/var/folders/dp/_9m3s06n48q7t5z9828ngwdw0000gn/T/gstack-sketch.afFIZ9/sketch.png` (three states: the preview in the group chat, the link opened by a receiver, the curator's Shortcut).

1. **Capture (curator), synchronous and fast:** the Shortcut or extension sends the source link; the server saves the post, creates a random, non-enumerable short id, and returns `…/s/<id>` immediately. It does not wait for cross-service matching. Latency budget: 1.5 s. The 3 s limit is enforced on the server: if saving the post takes longer, the server answers before 3 s with the original link. iOS Shortcuts have no request timeout or error handling, so the Shortcut copies the response only if it contains a `/s/` link and otherwise copies the original link from the share sheet, so sharing never breaks.
2. **Resolve, asynchronous:** after the response is sent (Vercel `after`/`waitUntil`), the server takes the source link (Spotify, Apple Music or Deezer), gets artist, title, duration and ISRC when available, and looks up the same track on Deezer (`track/isrc:` first, then search), Apple (iTunes Search) and Spotify (Web API: ISRC search first, then text search). Each service has a 4 s timeout. Matches are stored with the post.
   - **Match acceptance:** exact ISRC match, or else normalized artist and title equal (case, accents, "feat." and "- Remastered" suffixes stripped) and duration within ±3 s. Anything else is not a match, and that service gets a search link. Each stored match records its method (`isrc`, `text+duration`, `search-fallback`), so wrong matches can be audited.
   - **YouTube:** always a search link (`youtube.com/results?search_query=artist+title`); no API in this test.
3. **Preview:** the OG image (`@vercel/og`) shows the cover, title, artist and "partagé par {name}". The weekly count is listed with the minor findings.
4. **Receiver page (`/s/<id>`, no account):**
   - **Primary button:** on a first visit (no stored choice), the sharer's source service. On later visits, the receiver's last choice, stored in localStorage only (no cookie, no server-side id). Other services are an equal row of buttons below.
   - **Link formats:** plain https URLs only (`open.spotify.com/track/…`, `deezer.com/track/…`, `music.apple.com/…?i=…`, YouTube search), never custom app schemes. Inside in-app browsers these may open the web player instead of the app; that's accepted for the test. If matching is still pending or failed, the button opens that service's search for "artist title".
   - **Below:** the sharer's last 8 tracks, styled as in DESIGN.md, and "Partage le tien → installer le raccourci".
   - **Referral path:** "Partage le tien" goes to `/raccourci?ref=<post id>`. That page stores the ref in localStorage, and the signup page writes it to the new profile (`profiles.referred_by_post`). The iCloud Shortcut link itself carries no ref; attribution happens at account creation, which every capture needs.
   - **Visibility:** the page and the strip show only posts readable by anyone (all posts are public today; the `posts` read policy is `using (true)`). If private posts are added later, they are excluded and get no share link. Curators are told at onboarding that their shelf is visible to anyone who has the link.
5. **Logging, privacy-minimal:** no cookies and no visitor identifiers (no IP hashing). Store aggregate events only: page view, button tap (each tap records the service and the match method the button used at that moment: `isrc`, `text+duration`, `search-fallback` or `pending`), and "Partage le tien" tap. Views are counted client-side, so link-preview bots don't count. Events are kept for 90 days. Because nothing identifies a receiver, no consent banner is needed.
   - **Matching failure, per service:** no accepted match (method `search-fallback`) after resolve has finished or timed out.
   - **Before the curator test:** check the primary button in the WhatsApp, Messenger and Discord in-app browsers, on iOS and Android.
6. **Explicitly not built for this test:** group shelves, articles and books links, receiver accounts, the DESIGN.md dashboard rework.

## Open Questions
- Is the cross-app problem real in the founder's own groups (do members use different streaming apps)? This is unverified; the Assignment should answer it.
- How good does matching need to be? Remixes and singles often miss; what miss rate makes curators stop using the link?
- Will curators accept one extra tap (the Shortcut) instead of the native share button?
- Does the founder resume sharing daily? His own posting stopped 7 days ago.

## Success Criteria
Test group: 5 curators, not counting the founder, all on iOS or desktop Chrome. After 2 weeks:
- At least 3 of the 5 share on boredboard on their own on at least 5 different days. This is premise 1.
- boredboard links make up at least 30% of the music links those curators post in their groups (they send chat screenshots). This is the threshold set by the second opinion.
- At least 1 new account per curator makes its first capture with a referral: the "Partage le tien" install link carries `?ref=<post id>`, and the new account stores it at signup. That ties the new account to the curator whose link they came from.
- At least 80% of receiver taps on Spotify, Deezer and Apple Music buttons, computed from each tap's recorded match method, open an accepted match (`isrc` or `text+duration`) rather than a search fallback. YouTube taps are excluded, because YouTube is always a search link in this test.

If these are met, the next step is the next 15 users through the same groups. If not, the reason (habit, friction, matching) decides what to change before any growth effort.

## Distribution Plan
Web service on the existing Vercel deployment and CI (`.github/workflows/check.yml`). The iOS Shortcut is distributed by iCloud link from `/raccourci`; it needs updating to copy the returned `/s/<id>` link.

## Dependencies

## Reviewer Concerns

### R2-1 — completeness (blocking)

**Problem**

> The referral success criterion depends on a ref surviving from the receiver page to account signup, but the path is not specified. 'Partage le tien' leads to `/raccourci` and then an iCloud Shortcut link, which cannot carry a query parameter into the app or into a later signup. Nothing says where the ref is held between the tap and signup (URL through `/raccourci` to the signup page, localStorage, or a field the Shortcut sends), or how a new user's first capture is tied to that account. Without this, the criterion cannot be measured.

**Remedy**

> Specify the referral flow end to end: `/s/<id>` → `/raccourci?ref=<post id>` → signup, with the ref kept in the signup URL or in localStorage until signup and written to the new profile, and the Shortcut set up with that account. State that a referral counts when that account's first post is saved.

### R2-2 — completeness (blocking)

**Problem**

> The 80% criterion needs each tap tied to the match method that was served when it happened: matching is async, so the same service on the same post can be a search fallback at first and an accepted match later. Logging lists 'button tap per service' and 'match method per service' as separate aggregates, so the share of taps that opened an accepted match cannot be computed.

**Remedy**

> Make each tap event record the service and the match method the button used at tap time (`isrc`, `text+duration`, `search-fallback`, or `pending`), still with no visitor identifier. Compute the 80% from those events.

### R2-3 — feasibility (blocking)

**Problem**

> iOS Shortcuts' 'Get Contents of URL' has no configurable timeout and no try/catch: a slow request waits for the system timeout, and a network error stops the Shortcut with an error and copies nothing. So the 3 s hard timeout and the 'copies the original link instead' fallback, which the 'sharing never breaks' promise depends on, cannot be done on the client as written. The extension's failure behavior is also unstated.

**Remedy**

> Enforce the 3 s limit on the server (return the original link, or an `/s/<id>` whose matching is pending, before 3 s). In the Shortcut, check whether the response contains the short URL and otherwise copy the original link. Accept and document that a full network failure halts the Shortcut, or test a workaround. Specify the same fallback for the extension.

### R2-4 — clarity (minor)

**Problem**

> The design text refers to 'the minor findings', which belong to the review and are not in the document. A reader can't tell whether the weekly count was dropped or deferred.

**Remedy**

> Say the weekly count is dropped for this test, or list it as a deferred item in the document.

### R2-5 — consistency (minor)

### R2-8 — feasibility (minor)

**Problem**

> Exact artist equality across services often fails for multi-artist tracks: Spotify returns an artist array, Deezer a main artist, and iTunes a joined string such as 'A & B'. iTunes Search also cannot look up by ISRC, so Apple always relies on text plus duration. Correct tracks will fall back to search more often than expected, which works against the 80% criterion.

**Remedy**

> Compare on the primary artist, or on whether the artist sets overlap, and expect Apple's match rate to be lower than Spotify's and Deezer's.

### R2-9 — completeness (minor)

**Problem**

> If the background resolve is killed or crashes, a post stays pending for good with no retry, and the 'matching failure' definition ('after resolve has finished or timed out') does not cover a resolve that never finishes.

**Remedy**

> Mark matching as failed after a fixed window (for example 30 s), or retry the resolve the first time `/s/<id>` is loaded while matches are still pending.
